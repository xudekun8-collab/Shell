# 消融实验记录

> **口径声明（2026-11-08 补，已重跑验证）**
> 本文件下方表格是"时间项仍占 0.25 权重"时期的记录（默认组 Recall@3 0.8611 / MRR 0.8209）。
> 此后时间项已降级为 `occurred_at ±2 天` 粗筛、重要性权重 0.04，当前代码的真实结果以
> `data/eval_result.json` 为准：默认 Recall@3 0.8333 / MRR 0.8077 / 命中 30-36，
> 困难子集 0.8824 / 0.8679 / 15-17，时间配对子集 0.5000 / 0.4375 / 3-6。
> 论文与基线台账一律引用 `eval_result.json`；本文件的旧表格只作历史对照，不要引用其中数字。

## 打分定义（前几轮已定，本轮不改权重）

- score = 0.55*重合度（字符二元组 Jaccard） + 0.25*时间匹配 + 0.04*重要性 + 0.08*类型。
- 时间匹配：解析 query 时间词（昨天=1/前天=2/上周=7/上个月=30/上周三=4/下个月=未来30天/今天=0），
  time_score = exp(-0.15 * |目标日期 - occurred_at|)，解析不出时间词记 0。
- 重要性 importance/5；类型 event=1.0、session=0.8。

## 干净数据上的结论

30 条干净 query（目标与其它记忆字面差别明显）时，四组 Recall@3 几乎相同：

| 权重组 | Recall@3 | MRR |
|---|---|---|
| 默认 | 0.9667 | 0.9204 |
| 去掉时间项 | 0.9667 | 0.9204 |
| 去掉重要性项 | 0.9333 | 0.9256 |
| 去掉类型项 | 0.9667 | 0.9204 |

结论：重合度一项已能把目标排到第一，时间项和重要性项没有发挥空间，消融看不出差别。

## 类型项的适用边界

类型权重只在 session 记忆进入候选时才影响排序。recall 已放开为 event + session 两类，
session 需 overlap > 0 才进候选。本数据集里只有少数 query 与 session 摘要字面相关，且
session 记忆从未进入 top3，所以「去掉类型项」与默认组 Recall@3 完全一致——类型项是活代码，
但在这批 query 上观测不到召回差异，属于 session 摘要与事件问答本质不同，不是实现失效。

## 时间项的检验子集

设计动机：要让时间项“有决定权”，必须有内容几乎相同、只差日期（occurred_at）的配对记忆，
否则重合度一项就把胜负定死了。为此追加了 6 组“昨天 / 上周三”配对记忆与 6 条带时间词的 query。

结果（--time 子集，6 条）：

| 权重组 | Recall@3 | MRR |
|---|---|---|
| 默认 | 0.6667 | 0.6402 |
| 去掉时间项 | 0.6667 | 0.6402 |
| 去掉重要性项 | 0.8333 | 0.6905 |
| 去掉类型项 | 0.6667 | 0.6402 |

「去掉时间项」与默认持平（都是 4/6），没有掉分。原因：这 6 条配对记忆的正文里本身就写了
“昨天 / 上周三”这类日期词，重合度已能靠正文日期词区分“昨天版”和“上周三版”，时间项只是
增加了分差、没有改变排名。真正要时间项起决定作用，需要正文完全不含日期词、只在 occurred_at
上区分；本轮内容按约定原文未改，所以时间项在 --time 子集上仍然观测不到差异，如实记录。

另外「去掉重要性项」在 --time 子集上升到 0.8333：这些“昨天版”记忆 importance 都是 3，
而存在 importance=5 的同主题“昨天”记忆把它们挤下去，去掉重要性后反而更容易命中。

## 时间项诊断

36 条 query 中可解析出时间词的为 35 条（仅“我孙女啥时候来看我的”没有时间词），
比例 35/36，时间项在本数据集上具备统计意义。

## 结论约定

改完若默认组仍不是最好，如实保留结论，不再继续调参凑数。

注：recall 里的重要性 tie-break（分数差小于 0.03 时 importance 高者优先）属于召回后处理，
不进入消融实验的打分排序；实验只测纯打分。

## 时间项降级（最后一轮）

上一轮把 6 组配对记忆正文里的“昨天 / 上周三”日期词去掉后，用“昨天版”作真值做离线分析：
去掉时间项后 Recall@3 仍是 3/6，不掉分（时间项只改变排名、没跨过 top3 边界），
但 MRR 会掉（例如“我昨天买的什么菜”的正确记忆从第 17 名掉到第 65 名）。说明时间项作为
打分加性项对 Recall@3 不敏感，于是按预案降级：

- WEIGHTS 删掉 time 项，score 只剩 overlap + importance + type。
- 新增 time_prefilter：query 有时间词时，先用 occurred_at 粗筛（目标日期 ±2 天）再打分。
- eval 的 GROUPS 改为：默认 / 去掉重要性项 / 去掉类型项 / 时间预过滤。

降级后离线看，“时间预过滤”能把部分时间配对 query 的正确记忆排名前移（65→28、69→30），
但 Recall@3 仍是 3/6。原因：这些 query 与正确记忆存在字面错位（如“买的/买了”“什么菜/菠菜”
二字组不重合），重合度接近 0，时间粗筛救不回 top3。这是 2-gram 重合度的已知局限，如实记录。

## 交互轮数统计口径

主动问候为了进上下文，会写入 `interaction_events` 一条 `input_type='greeting'`、
`raw_input=''` 的记录（这是模型上下文唯一来源 recent_turns 读取的表，必须写这里才看得见）。
该问候不占 conversations.msg_count、不触发压缩。统计“用户交互轮数”时必须按
`input_type != 'greeting'` 过滤，否则轮数会被问候虚高；问候行不是用户输入，也不计入
情绪/意图等用户行为统计。
